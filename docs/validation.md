# 回放尖塔实机验收

## 复现环境

Windows x64，.NET 9，游戏主分支 `0.111.1 / cc1f9462` 和测试分支 `0.113.1 / d09d48e5`。游戏安装提供本地引用程序集与资源。候选版本为 `0.1.0`，本轮安装包的源码提交为 `ab9642d`。测试工具使用私有副本和独立用户目录，关闭 Steam 集成，普通场景设为静音。声音专项测试将游戏输出定向到 Steam Streaming Speakers 虚拟设备。

```powershell
dotnet run --project tests/Storage/StorageTests.csproj -c Release
python scripts/acceptance.py 'D:/Games/Slay the Spire 2' --name review --ffmpeg 'C:/Tools/ffmpeg.exe' --campaign
```

`--ffmpeg` 启用有声、静音、取消、清晰度和同步测试。`--campaign` 额外重演三幕路线，`--campaign-media` 还会导出三幕图集及视频。`--ordinary` 使用铁甲战士的原版生命、牌组、金币和遗物，一直打到这局自然结束。`--foreign-replay` 接受另一游戏构建录制的真实文件，用单独存档核对导入、时间线和卡牌统计。在另一版本的本地游戏目录执行同一命令，会写入独立的版本子目录。每次完整验收使用新的会话名。原始日志、私有回放和哈希记录在 `.local/<会话>/<游戏版本>/`。

下列整局原始样本和性能对照录于 `799a1e3`。安装包另含事件领奖、图集和零输入战斗修订。

## 实测样本

主分支的三幕测试走完 48 层，游戏登记为胜利。原生战斗重播检验 30 场战斗的 213 个状态校验点，同时覆盖跨幕地图和最终建筑师事件。在进入第一层之前，测试脚本为铁甲战士设置了 1,000 点生命和强化牌组，随后按地图实际连接行进。该路线用于复现跨幕、结局和存储负担。五角色测试使用各角色的原版起始牌组。

| 记录样本 | 房间记录 | 本地记录目录 | 便携文件 |
| --- | ---: | ---: | ---: |
| 一次主分支三幕胜利 | 52 段，含 30 场战斗 | 4,319,185 字节 | 851,339 字节 |
| 键鼠实打两层，保存于第二次战斗中 | 起始地图与两场战斗 | 160,081 字节 | 40,888 字节 |

此三幕样本的 720p 有声 MP4 为 160,511,726 字节，共 714.7 秒。已从头到尾解码 21,441 帧 H.264 画面和 AAC 立体声音轨，两条轨道结束时间一致。导出进程正常完成，三个声音抽样峰值为 −19.3、−15.9 和 −19.6 dBFS。完整日志另有四条 Godot 资源句柄异常，整局导出的严格日志验收仍待解决。

测试分支同一路线新录得到 29 场战斗，含 7 场玩家输入前由自动出牌取胜的战斗。原生回放逐一核对了这 7 场的状态和奖励；52 个节点的逐房断言通过。一次完整回归日志仍有 Godot 资源预加载的 Invalid Task ID，计为日志未通过。

三幕样本同时保留原始记录和自动导出文件，共约 4.93 MiB。每场战斗的回合数、选择次数、随模组加入的状态，以及中途读档次数都会改变体积。普通对局记录只写动作、房间入口和游戏原生校验数据。显存读回、声音采集和视频编码均在玩家启动导出时启用。

键鼠样本使用只启用《回放尖塔》的主分支游戏。铁甲战士打出 7 次打击，共扣 41 点生命，2 次痛击扣 15 点，1 次防御获得 5 点格挡。两次致死打击分别只计敌人剩下的 1 点和 4 点。从打击的贡献列表跳回首层并逐手播放后，已导出文件中的每项内容与记录目录逐字节一致。新版两层图集包含地图落点、两次打击命中和战斗奖励四张实机截图。

主分支与测试分支的安装包分别为 150,726 和 150,729 字节。解压后各占 342,284 字节，含 DLL、模组清单和许可证。FFmpeg 可由玩家指定，或在首次导出视频时单独安装。

## 前一轮的图集目标帧与首次导出

使用同一台 Windows 笔记本的 RTX 4070 Laptop 独显和 1280×720 游戏画面。主分支使用同一份回放分别在上一版和本版的独立测试会话导出，计时从导入回放后开始。每次首次导出使用空图集缓存。三幕样本沿用前述强化牌组。

| 主分支回放 | 上一版首次 | 本版首次 | 本版重复 | 截图张数 |
| --- | ---: | ---: | ---: | ---: |
| 两层实录，含起始地图 | 17.750 秒 | 15.313 秒 | 32 毫秒 | 4 → 4 |
| 三幕，52 节点 | 279.260 秒 | 238.590 秒 | 65 毫秒 | 58 → 79 |

地图在展开后取图，奖励在原生面板填充后直接推进到淡入结束再取图。最终 Boss 的空奖励界面只用于前进，跳过该空面板截图。战斗在目标卡牌和原生伤害数字同框时取图，显示已结算的敌方生命值。两层实录中的打击分别显示伤害 9、剩余 17/46，以及伤害 6、剩余 4/10。三幕中带实际扣血标注的照片从 8 张增至 30 张，整套图集从 6.44 MB 增至 11.81 MB。主分支新图集所有 JPEG 和离线图文链接均已核对，交付目录各含 `index.html`、`index.txt`、`images/`。

上一版的三幕会话在 52 个节点各重载 46 个角色资源。新版本在图集逐层切换期间保留角色资源，只在首层载入 46 项，其余 51 个节点均是 0 项。原生日志的角色预载耗时合计由 55.857 秒降至 14.957 秒。新版三幕统计中，打开房间及切换花了 203.555 秒，其余推进动作、取帧和写出共 34.974 秒。房间的原生清理、随机数恢复和战斗状态校验仍走原回放路径。

主分支两层的完整日志通过。测试分支也导出了 52 节点的独立三幕样本，首次用时 259.450 秒，重复导出 65 毫秒，共 71 张 JPEG。两个三幕图集均已完整生成。两次运行的完整日志各有 2 条原生卡牌池重复回收错误，未通过日志校验。旧版三幕样本也出现过同类错误。

同一安装包用一局常规铁甲战士回放完成了古神选项、战斗原生状态校验，并经主菜单的「生成整局直播贴」完成导出。两次运行的完整日志均通过，隔离环境的存档及设置哈希一致。

## 图集会话内换层

使用同一三幕回放、同一台机器和 720p 游戏画面做无图集缓存对照。计时从导入后点生成开始，到 HTML、正文和 JPEG 全部写出为止。

| 测量 | 逐层返回主菜单 | 会话内换层 |
| --- | ---: | ---: |
| 首次导出 | 230.164 秒 | 164.613 秒 |
| 打开房间与换层 | 195.150 秒 | 129.657 秒 |
| 房间内推进、取图和写出 | 34.974 秒 | 34.916 秒 |
| 重复导出 | 49 毫秒 | 49 毫秒 |

首个房间从主菜单进入，其余 51 个房间直接切换。新版累计关闭旧房间 1.958 秒、角色与幕资源预载 1.201 秒、从检查点恢复房间 126.178 秒。最后一项含房间资源预载和原生场景创建。每层仍恢复独立检查点，并由原生回放执行动作和校验。

独立的整局验收在每次原生回放初始化前比较记录中的对局与角色随机数，52 个房间的两组随机数状态均一致。图集定位期间实际经过的 178 个原生战斗校验点均通过。

两版导出的 52 个节点标题与 79 张图的文件名、位置和说明逐项一致。已核对跨幕地图、出牌命中、奖励与最终 Boss 的实机画面。伤害数字位置和动画元素随帧进度有细微变化。

卡牌池追踪以同一次借出的巨镰节点为准。旧场景移除时，消耗特效的退出回调已归还该节点。原生两秒延时回调随后又尝试归还同一节点，且这时下一层已经加载。回放中的延时回收现在先确认该特效仍在场景中，并仍持有卡牌节点。原生对象池与退出回调照常运行。保留旧换层流程、单独加回收修复后，原先出错的 10 节点片段从两次重复回收降至零，入口随机数和 30 个原生状态校验点均通过。主分支三幕的重复回收从 2 条降至 0 条。测试分支同一份 52 节点样本首次导出 182.534 秒，生成 71 张 JPEG，重复回收为 0。两次整局导出都通过完整日志校验。

从主菜单生成图集及常规对局回放均通过完整日志校验，两项测试的隔离档和设置文件哈希一致。

## 核显与独显

使用主分支安装包、同一台 i9-14900HX 笔记本、32 GB 内存，分别指定 Intel UHD 核显与 RTX 4070 Laptop 独显。每块显卡做两组开关录制的配对测试，第二组交换顺序。实际读回的画面均为 1280×720，游戏目标为 60 帧，所有样本的前台时间占比均为 100%。同一种子走相同的四个操作，核对最终手牌、敌人和玩家状态。

| 战斗样本 | 关闭录制时 P95 帧时间 | 开启录制时 P95 帧时间 | 开启录制时游戏进程工作集峰值 |
| --- | ---: | ---: | ---: |
| Intel UHD Graphics | 16.84 ms | 16.92 ms | 0.73–2.25 GiB |
| RTX 4070 Laptop GPU | 16.75 ms | 16.70 ms | 1.41–1.42 GiB |

另将同一游戏进程限制在两个逻辑 CPU，在核显上重复三组，关闭和开启录制时的 P95 均值分别为 17.00 和 17.04 毫秒。帧时间取各轮 P95 的配对均值。这台机器的短战斗中，开启记录后的 P95 处在相近水平。核显与独显共享同一颗高性能 CPU。更慢的 CPU、8 GB 内存和其他模组组合仍需要在对应设备上测量。表中的内存是整个游戏进程的工作集。

游戏的 Windows 最低配置列为双核 2.0 GHz、4 GB 内存和 1 GB 显存。以下实测使用本机的实际内存容量。[Steam 商店系统需求](https://store.steampowered.com/app/2868840/Slay_the_Spire_2/#sysreqs)

本版从 64 位 Windows 10 2004（build 19041）起，在导出 MP4 时直接检测进程音频采集能力。微软示例注明 build 20348，OBS 的同一采集接口支持 Windows 10 2004 起的系统。本机 Windows 11 build 26200 已实测；Windows 10 22H2（build 19045）的实际声轨仍待该系统确认。普通录制、播放器和图集走游戏自身的接口。[Microsoft 进程回环采集示例](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/) · [OBS 按进程采集](https://obsproject.com/kb/application-audio-capture-guide/)

另在 Intel UHD 上测量单次编码的 720p 导出。9.6 秒的文件为 1,675,107 字节，临时目录中只出现该 MP4。导出前游戏工作集为 2.10 GiB，导出中游戏和 FFmpeg 的合计峰值为 2.48 GiB。288 个输出帧中有 12 个复用前一帧。配置较低的机器可以先照常打牌，之后再按需要开一次导出。

## 如何核对

| 链路 | 核对内容 |
| --- | --- |
| 战斗录制与回放 | 实际出牌、抽洗牌、药水、嵌套选牌、随机目标、敌方回合和同一战斗的原生校验点 |
| 非战斗房间 | 房间入口、事件选项、营地休息、商店购买、开宝箱、战后金币和卡牌、地图落点 |
| 原生选牌 | 脑蛭五选一、商店删牌、所有候选与原局选项、暂停时牌组不变、跳回选牌节点、继续后高亮并完成单次变更 |
| 保存与分享 | 继续游戏后同一楼层的不同访问，独立用户目录导入同一文件两次，播放前后比较正式存档、原生回放、备份与历史的哈希 |
| 回放库 | 从卡牌、时间线、楼层选择器定位，暂停、逐手播放、跳回合，打开记录目录，生成实机图集和直播贴 |
| 有声 MP4 | 解码两条媒体流，核对帧尺寸、时间戳与音量，用三次闪光和同进程测试音测同步，并用另一个进程的声音测试隔离 |
| 录制负担 | 同一角色、同一种子与同一组输入交替开启、关闭记录，比较实际帧时间分位、内存、记录字节以及最终战斗状态 |

回放库另用每局 52 层的模拟索引测量磁盘读取。文件缓存已热时，100、500、1,000 局的读取中位数分别为 7.9、37.0、73.7 毫秒，托管分配约 1.6、8.0、16.1 MiB。打开窗口后在后台读取索引；关闭再打开由最新窗口接收结果。

绘制、声音和录制性能以实际完成的对照样本为准。成片编码 H.264/AAC。每个验收阶段在单独的游戏进程执行，原生实测必须能找到阶段成功标记。验收脚本可通过 `--validator` 接入完整日志验证器。

## 人工验收

1. 自己打一场熟悉的单人战斗。在一个容易记住的节点停顿几秒。回主菜单打开回放，找到这个动作，检查节奏、暂停和跳转手感。
2. 在全局卡牌统计中选一张常用卡，查看详情并从记录回到现场。试一下键盘、手柄或常用显示比例。
3. 导出一段有声 MP4，听一次抽牌、命中或结束回合。打开整局直播贴目录，按文件名顺序选择截图，读一遍配文。以你愿意实际分享的效果作为验收标准。

`scripts/review.ps1 -GameVersion 0.111.1 -Session review` 可打开已经准备好的隔离实机环境。
